# Band2Tab：候補補完からMu本体の追加学習へ

2026年11月20日 / 担当A / 発表に向けた追加実験の記録

## 1. 今回の目的と判断の順序

前回は余計な音符を消す学習で小幅改善したが、必要な持続音を消す例があった。今回は、見落とした音を補う方向へ進めた。正解音符・候補・学習・設定選択・評価を分け、「学習を回した数」より「どの仮説をどの比較で採択したか」を重視した。

第1周：別AIのギター候補に、Muの予測を上下1オクターブに動かした候補も加えた。元の音符・開始・終了は変更しない。小型NN、持続音への影響を学ぶ補助課題、取得済みの多様な教材を比較した。

第2周：少数の正例を含む数値特徴に対し、ニューラルネット以外の勾配ブースティング木を比較した。どちらも内部確認で4指標を保護する改善を確認できず、自動的な追加は採用しなかった。

第3周：正解を見て候補を選ぶ診断でも回復できない見落としが多かったため、Mu本体へのLoRA学習に進んだ。正解音符から作った記号列の復元検査を先に通し、元の大きな重みを固定したまま小さな行列だけを学習する。

評価は、音符F1＝楽器・音高・開始50ms以内の一致、Frame F1＝20msごとの鳴っている音（MIDI 23〜88）の一致、全音一致＝活動中の全音集合が完全に合う割合、終了F1＝さらに音の終わりも許容差内か、の4つを見る。終了の許容差は50msまたは正解長20%の大きい方。各表は区間・データ領域ごとのマクロ平均で、F1は単純な正解率ではない。

今回の追加学習は教師あり学習である。音符ラベルとの誤差を小さくする。強化学習を新たに実施したわけではない。新しい外部データの大量取得より、取得済みデータの用途拡張と音色加工を優先した。

## 2. 教材と候補：何を増やしたか

前回の内部確認24条件を継承し、同じGOAT演奏・Slakh元曲の別加工を学習側へ流さなかった。既存の訓練側に、GuitarSet 8区間、同期検査済みGuitar-TECHS 32区間を追加した。Slakhのフルミックス、加工済みベースも使った。最終評価用の11元曲は今回も未開封である。

学習側の有効候補17,048個のうち、Muが見落としていて正解の開始に合う補完候補は338個、約1.98%。そのうち324個は、単独で加えてもFrame F1を下げない候補だった。大半は不要な候補であり、数を増やすだけでは精度が下がる。

| 訓練教材 | 有効候補 | 正しい補完候補 |
| --- | --- | --- |
| GOAT由来のG＋B・干渉なし／あり | 8,944 | 207 |
| 加工済みベース | 2,000 | 14 |
| Slakhフルミックス | 4,485 | 99 |
| GuitarSet | 919 | 18 |
| Guitar-TECHS | 700 | 0 |

Guitar-TECHSのこの区間群では、今回の候補規則で新たに補える正例はなかった。誤ったオクターブを追加しないための負例として働くが、「正例を大量追加した」とは説明しない。音色違い・加工違いは新しい独立演奏に数えない。

新しい補完器は366特徴を使う。CQTで捉える候補音高と倍音の証拠、原音とG/Bステムの比較、アタック・音量、既存音との重なり、候補を出した経路などである。正解ラベルは教師計算にだけ用い、特徴や候補生成には渡さない。

## 3. 小型NN・持続保護・木モデルの結果

4方式を各3 seed（初期値と抽選の設定）、各800更新、計12回学習した。全方式で366入力・同じ小型MLP構造を使い、候補と教師・教材を変えた。音符が正しいかに加え、その候補の追加がFrame F1を下げないかを学ぶ補助出力も比較した。

| 比較方式 | 変更したもの | 内部確認での採択 |
| --- | --- | --- |
| 別AI候補のみ | YourMT3のギター候補を選別 | 厳密な改善なし |
| オクターブ候補を追加 | Muの上下12半音も候補化 | 厳密な改善なし |
| 持続音の補助教師 | 発音の真偽＋Frameへの寄与 | 厳密な改善なし |
| 多様な教材を追加 | 元の教材抽選の25%を他領域へ | 厳密な改善なし |

共通の元教材は、適切な別AI候補がある60条件。追加側の利用可能な条件は103条件。基準の抽選に同じ乱数列を使い、3 seedすべてで一致をハッシュ確認した。NNの正例損失重みは8、AdamW、学習率0.0003。各方式の最終800更新だけを使い、中間重みを大量に探して選ばなかった。

さらに、分岐ルールを順に加えて誤りを補う勾配ブースティング木で元教材／多様化を比較した。最大200反復、15葉、深さ5、正例重み8。各3 seed、計6回fitしたが、内部確認で採択できる改善はなかった。この規模・設定では木の学習はほぼ決定的で、seedを変えた結果を独立した性能の証明とは扱わない。

木の元教材群では、内部の音符F1が+0.065ポイント、Frameが+0.024、終了が+0.072となる設定もあったが、全音一致が0.174ポイント下がり不採用だった。正例が少なく候補スコアが0.5未満にある可能性も確認し、追加学習なしで0.05から1.1までの9段階・G/B別81通りへ探索を広げた。NN4方式と木2方式の計486設定を内部だけで比較しても、採択できる改善はなかった。

設定選択は内部24条件でのみ行った。各データ領域の音符・Frame・全音一致・終了F1を保護し、基準から厳密に改善しない場合は明示的な「追加なし」にした。基準と同点の低い閾値を、別の入力へ無条件に適用しない。原結果と以前の補正案を保存し、アプリの既定モデルは変更していない。

## 4. 診断：候補にない音は選別器では作れない

固定後に、反復16条件と既知14条件を確認した。追加候補を全部入れると大幅に悪化した。一方、正解ラベルを見て正しい候補だけを選ぶ診断は、候補不足がどれくらい残るかを見るためのもので、利用できるAIの成績ではない。

| 反復16条件 | 音符F1 | Frame F1 |
| --- | --- | --- |
| 基準Mu＋分離 | 81.842% | 80.688% |
| 候補を無選別で追加 | 64.060% | 63.417% |
| 正解を参照した理想化診断 | 83.709% | 81.879% |
| 今回の採択方式：追加なし | 81.842% | 80.688% |

16条件で1,607候補のうち、真の補完候補は35音だった。基準の見落とし148音の多くを候補集合に含められていない。既知14条件でも1,399候補中43音で、音符F1は基準67.061%、無選別50.233%、正解を参照した診断70.444%だった。

さらに、以前の「オクターブ違いのギター誤検出58音」を一対一照合し直すと、57音では対応する正解音が既に別の予測で検出されていた。この誤り群は、音を補うより余分な音を抑える対象だった。倍音を別音として拾った可能性はあるが、照合だけで音響的な原因までは断定しない。

この診断を受けて、分類器の大型化や閾値の調整を続けるより、音符を生成するMu自身の追加学習を優先した。候補選別の失敗から、次の学習対象を変えたことが今回のセルフフィードバックである。

以前のC7補正との組合せも記録したが、今回の追加なし案はC7単独と同じである。前回の改善を新しい追加学習の成果として二重に数えない。発表では「不採用の理由」と「次の仮説へのつながり」を示す。

## 5. Mu本体へのLoRA：何を学習するか

Muは音声のメルスペクトログラムを条件として、音高・発音・終了・楽器を表す記号を順に生成するTransformerである。今回はその最後の8層のAttention出力に、rank 8のLoRAを追加する。元の約3億個の重みは固定し、131,072個の追加パラメータを学習する。音符の選別だけと異なり、生成する音高・時刻そのものを変えられる。

教材は、学習側のギター108・ベース130、計238個の5秒窓。ギター・ベースの推定分離ステムと正解音符を対応させる。分離漏れを含む教材もあるため、完全な単一楽器の正解音声とは限らない。評価用の参照音符は書き換えない。

正解音符を100Hzの時刻記号、音高、楽器、持ち越し音、終了記号へ変換した。窓内で開始・終了が分かる3,908音を公式のデコード処理で戻し、音高と時刻が復元できることを確認した。最大丸め誤差は5ms以内。窓をまたぐ音の持ち越しと同音重複はモデルの表現に合わせ、訓練のみに重複整理を適用した。

| 比較条件 | 学習方法 |
| --- | --- |
| 学習なし | 同じGPU・重み型・推論設定で新しく推論 |
| gold | 正解の音符記号に対する交差エントロピー＋元モデル保持KL |
| gold_tone | 同じ音源・抽選に、訓練時だけ音色加工を追加 |

各条件の初期値・教材の抽選・更新数を揃え、120更新、1更新あたり5秒×2窓、学習率0.00001。KLは元モデルの出力分布を急に変えないための損失で、係数0.5とした。音色加工は時刻を動かさないEQを中心に、単独の加工ベースにのみ追加の歪みも許した。別の演奏者が増えた意味ではない。

まず内部確認のGOAT 4条件＋Slakh 1条件で、同じ計算条件の基準と比較する。最終120更新だけを使い、途中の多数の重みから良いものを探さない。その後、固定済みの2仮説を従来16条件でも診断し、不採用の場合も記録する。少数の内部条件・1 seedの試行であり、未知曲への一般化の証明にはしない。

## 6. 追加の自己点検：楽器の細分類を保持する

最初のMu学習では、ギターの正解記号を一律にclean electricの代表program 26へ、ベースをprogram 33へまとめていた。音高・時刻のラベルとは別に、学習のために置いた細分類である。しかし元のMu出力では、ギター108窓中55窓が歪み系program 29、25窓がアコースティック系program 24を主に出していた。80窓で、元モデルと異なる細分類を教師として与えていた。

この違いが悪化の原因かを確かめる追加比較を行った。各窓の元Muで長く発音した自パートのprogramを使い、音声・正解音高・開始・終了・窓・更新数・学習率は変えない。細分類は元モデルからの疑似情報であり、正解の音色注釈を新たに得たわけではない。対象外のprogramしかない場合は元の一律指定へ戻した。

238窓中82窓のprogram記号だけが変わった。ベースは2窓がprogram 32へ変更。記号数とそれ以外の全記号が同じであること、3,908音の復元が再び通ることを検査した。この条件でも、加工なし／音色加工ありの2回を同じ抽選・120更新で比較した。

最終のファイル照合で、初回予備の実行中に手元の数値計算設定を更新したため、初回と細分類保持で、数値計算時に一時的に掛ける倍率（勾配スケール）の初期値が違うことが判明した。実際に使った初回の設定とソースをハッシュ一致で復元・保存し、同じ設定512で一律細分類の対照2回を再実行した。主比較はこの再対照と細分類保持で行い、初回予備2回は履歴として区別する。条件を揃えて再実行した結果、集計評価は初回予備と同じで、採否は変わらなかった。

さらに、追加学習後の音符をそのまま使うと正しい発音を動かす可能性があるため、基準と音高・開始20ms以内で一致する音符だけ、学習後の終了を使う方法も登録した。基準の音高・開始・件数はそのまま残す。変更幅は最大150msか元の長さの半分までとし、大きな不一致は無視する。これは新しいモデル学習ではなく、学習結果を安全に利用できるかを比べる後処理の実験である。

0・25・50・100%の終了変更量をギター／ベース別に内部5条件で選び、4指標を領域別に下げず厳密に改善した場合だけ比較案として残す。16条件の結果から閾値を選び直さない。今回の仮説は反復評価の失敗を見て立てたもので、独立テストの結果とは区別する。

## 7. Mu追加学習の結果：改善する指標だけで採用しない

| 同じ計算条件の16条件 | 音符F1 | Frame F1 | 全音一致 | 終了F1 |
| --- | --- | --- | --- | --- |
| 学習なし | 81.842% | 80.679% | 42.058% | 73.538% |
| 一律細分類・再対照・加工なし | 81.769% | 80.818% | 42.038% | 73.458% |
| 一律細分類・再対照・音色加工 | 81.769% | 80.814% | 42.038% | 73.458% |

Mu本体のLoRAは初回予備2・細分類保持2・条件を揃えた再対照2の計6回、各120更新、計720更新。表は数値計算条件を揃えた再対照と細分類保持の主比較である。全6回で元の大きな重みが変わらないこと、8層すべてで追加行列が実際に更新されたこと、教材の抽選が同じことを確認した。

元重みを固定しても、LoRAの追加出力で予測は変わるため、精度が下がる可能性はある。Frame F1はわずかに上がったが、音符F1・全音一致・終了F1が下がった。細分類を元Muに合わせても、改善は確認できなかった。最初の教師の細分類だけが悪化の原因だったとは結論しない。音色加工の追加効果も今回の範囲では確認できない。

内部5条件の数値も、実際に実行した設定・重みと対応させて記録した。初回予備の一律細分類は音符F1 50.418%、元Muの細分類は49.731%で、いずれも基準52.737%を下回った。初回予備は勾配スケールの初期値が違うため、細分類だけの効果を分離する主比較に混ぜない。学習後の終了だけを使う64設定の比較でも、内部で4指標を保護しながら厳密に改善する設定はなかった。これも新しい64回の学習とは数えない。

この表の基準は、CUDAでfloat32重み・float16計算を使って新しく推論した値。以前の保存済み基準とはごく小さな終了時刻差があり、Frameや全音一致が少し違う。各LoRAは同じ条件で再推論した基準と比べ、違う計算条件を一本の精度向上曲線に混ぜない。

今回の追加は、NN 12学習、木6fit、Mu LoRA 6学習の計24回。木の反復と勾配更新は異なるので合算しない。新しい比較案が従来案を上回ったという結論には至らず、既存の基準・前回のC5/C7比較案を維持する。前回の限定的な改善を今回の成功として数え直さない。

## 8. 発表への価値、次の優先順位、Macへの影響

研究上の価値は、候補数の不足と選別の難しさを分け、教師ありの補助分類からMu本体のLoRAまで、理由を持って比較した点にある。候補を増やしても真の補完は少なく、音色を増やしても新しい奏者は増えない。細分類の仮説を立て、他の記号と音声を固定して確認し、悪化した方式を採用しないという過程を発表できる。

次の優先1：余分な高い音と本物のオクターブ重音を区別する教材に絞る。取得済みの単音素材と音色加工から、単音の倍音／実際の2音を比較する合成教材を検討する。弦別音声は取得状況を確認して補充する。57/58の診断から立てた次の仮説で、今回まだ学習した成果ではない。見落としは候補生成・分離欠落・同音重複・短音の別に分析する。正解ステムを使う診断は到達可能性を見るために限定し、アプリで使える結果と区別する。

優先2：Muの更新範囲が最後の8層のAttention出力だけだったこと、1 seed・120更新の小さな試行だったことを踏まえる。次の追加学習では、同じ音符教師を保ち、更新範囲・学習量・元モデル保持の強さのうち一つずつ変える。音色増強だけを無目的に増やすより、独立した奏者や短音・ミュートの正例を補う。更新を広げると良くなるとは未検証である。

優先3：11/21までに追加比較を絞り、11/22に方式・重み・設定を固定して保留11元曲で初回比較する。そこで悪化したら基準を採用し、失敗例として説明する。11/23にBとデモを固定し、11/24に練習、11/25に発表する。コード名・拍・運指・TABの精度は別に検証し、今回の音符指標で証明しない。

Bのアプリ・元の12秒ZIP・基準JSON契約・既定の認識モデルは変更していない。今回の不採用モデル一式をBへ移す必要はない。Bは従来の基準と任意補正案の読込・再生同期・1か所編集・再保存・MusicXML出力の結合確認を継続できる。

全学習の成果をMacへ取り出し、チェックポイントのSHA256を照合した。Azureは最後に「停止済み（割り当て解除）」を直接確認済み。独立した終了処理で、学習・比較後に回収・検証・割り当て解除を行った。仮想マシンを稼働したまま次回を待ってはいない。

実測の集計は docs/measurements/feedback_20261120.json。再現コードは scripts/a_residual_cycle.py、a_residual_tree.py、a_mu_adapt.py、a_mu_native_cycle.py、a_mu_consensus.py。学習済み重み・音源・正解音符・認証情報は公開Gitには含めない。
