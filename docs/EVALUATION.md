# 発表で何を検証するか

## 学習と比較の位置づけ

独自学習は `band2tab/model.py` の **NoteCRNN（CNN + 双方向GRU）をゼロから教師あり学習する実験**です。既存モデルの追加学習ではありません。CQT画像から局所的な倍音の形をCNNで読み、前後の音の連続性をGRUで読み、B0〜E6の66音高それぞれに対して「発音開始・持続・終了」の確率を同時に予測します。1音を選ぶ分類と違い、複数の音を同時に出力できます。楽器指定（ギター/ベース）も入力しますが、楽器の自動識別精度を測るモデルではありません。

|比較|学習|検証したいこと|
|---|---|---|
|既存：Basic Pitch 0.4.0|公開済み重みを固定|既存技術でどこまで認識できるか|
|A0|GuitarSet + BabySlakh の単独パート|独自モデルの基礎性能|
|A1|A0に同じ分割内の他楽器を加えた混合音も追加|混合音への耐性が改善するか|

A0/A1は初期化seed17、同じ構造、AdamW、学習率0.001、batch4、4秒窓、同じ更新数です。現行スクリプトの1 epochは100回の更新であり、全曲を1巡する意味ではありません。5 epochは500更新、計2000窓をランダム抽出します。独立した曲が2000曲あるという意味でもありません。スペクトルノイズの追加オプション `--augment` はこの比較では使いません。変更要因を混合音の追加に限定します。

## 正解と分割

公式チェックサム確認済みGuitarSet/BabySlakhの音声と正解を使います。GuitarSetは進行の同じ演奏者違い・キー違いを同じ群にまとめ、BabySlakhは元MIDIのUUIDでまとめます。元曲・派生混合音をtrain/val/testにまたがらせません。本プロジェクト独自の群分割なので、先行論文の公表スコアと直接比較しません。分割は固定し、検証用データで音符化の閾値を決めた後にテストを行います。

現在の基礎データは421パート、独立群35。うちGuitarSet357パート、BabySlakh64パートです。派生混合音112パート（train45/val33/test34）は新しい独立曲ではありません。ギターとベースが両方とも含まれるよう、混合音は楽器別に抽出します。公表された誤注釈3パートと出力音域外を含む1パートは理由を記録して除外しています。BabySlakhは20曲の試作用合成セットで、本実験を大規模実録音評価と呼ばないでください。

## 指標をどう読むか

- **Note Precision（適合率）**：出した音のうち正しい割合。低いと余計な音が増えます。
- **Note Recall（再現率）**：正解の音のうち拾えた割合。低いと音抜けが増えます。
- **Note F1**：上の2つの釣り合い。音高はオクターブ込み、発音開始は±50msで照合します。
- **Offset F1**：開始・音高に加え、終了時刻も許容誤差内で合うか。許容誤差は正解音長の20%または50msの大きい方。
- **Frame F1**：20msごとの音高集合が合うか。特定時刻の音一覧に直結します。
- **音集合の完全一致率**：正解または予測に音がある時刻で、余分な音も欠けた音もない割合。単にCメジャーと予測できても、Aが抜けていれば完全一致になりません。
- **単音/2音/3音以上のFrame F1**：正解の同時MIDI音高数で集計し、ダブルストップや和音の難しさを分けて見ます。同音ユニゾンの弦の本数は数えません。

曲ごとのF1を平均し、ギター/ベース、単独/混合を別々に表示します。曲ごとの結果を残し、悪い例を削除しません。A1−A0の差は同じ曲で比較します。元曲群単位のブートストラップ区間も出しますが、群が少なくseedも1つなので優位性を証明するものではありません。

## 実行場所とコマンド

以下は **Azureの `~/music_ai_exp`**。先に `source ~/venv/bin/activate` を実行します。

```bash
bash scripts/a_train.sh
# 検証結果を見て設定を確定。精度が低ければ、テストを見る前に原因を調べる。
python scripts/a_freeze.py
bash scripts/a_test.sh
```

Basic PitchはPyTorch環境と分離したPython3.10環境 `.venv-bp` を使用します（現VMに作成・動作確認済み）。同じデータで推論し、結果を共通評価器で採点します。次は検証用の例で、テスト時には3か所の `val` を `test` に変更します。

```bash
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 .venv-bp/bin/python \
  scripts/a_baseline_predict.py --manifest data/manifest_clean.json \
  --split val --out reports/basic_pitch_val_predictions
python -m band2tab.report baseline --manifest data/manifest_clean.json \
  --predictions reports/basic_pitch_val_predictions --split val \
  --out reports/basic_pitch_val.json
python -m band2tab.report summarize reports/a0_val.json \
  reports/a1_val.json reports/basic_pitch_val.json \
  --out reports/presentation_val
```

既存モデルと2つの独自学習をまとめて固定テストする場合は、検証後に `bash scripts/a_compare_test.sh` を1度実行します。このスクリプト自身が設定を凍結するため、既に `a_freeze.py` を実行済みなら、個別のテストコマンドを使用します。

`comparison.csv`、`comparison.json`、`evaluation.md`、`note_f1.png` を出力します。数値は0〜1（0.7=70%）です。発表に貼る前に、分割名がvalなのかtestなのか明示してください。長い推論は既存の予測ファイルを検証して再利用できます。

## 研究としての価値と主張できる範囲

研究仮説は「楽器を指定した軽量な音響モデルに、他楽器の重なりを含む教師付きデータを追加すると、単独パートだけで学習するより混合音の音符検出が改善するか」です。改善しない場合にも、条件・原因・限界を示す比較実験になります。

プロダクトとしては、**コード名と実際のギター/ベースの音高を別に保持し、余分な音・抜けた音を確認しながら、弾けない運指を明示するTAB下書きへつなげる**点に価値があります。ただし、既存要素の統合だけで世界初・SOTA・全自動完全採譜とは主張できません。既存モデルより精度が低ければ、主採譜は既存モデルを用い、独自モデルは確認支援の候補として扱います。確認支援で誤りを見つけられる割合や編集時間の短縮は、別途B担当と測定が必要です。

音符評価だけでは、複雑コードの正解率、原演奏と同じ弦/フレット、奏法、TABの弾きやすさ、Macアプリの使いやすさは検証できません。それぞれ別の評価項目として扱います。特に音高だけから弦・フレットは一意に決まりません。

## 初回実験の扱い

500更新の初回比較はパイロット実験です。検証Note F1はA0=0.1007、A1=0.0956、Basic Pitch=0.6738。独自モデルの精度は実用水準と呼べず、A1による改善も未確認です。主採譜を独自モデルに置き換えないでください。確認支援としての有効性もまだ測定していません。

以後は学習曲数、訓練更新数、オンセットのクラス不均衡と誤検出を検証用データで調べます。追加モデルの最終比較には今回のテストを何度も最適化に使わず、Slakh reduxの重複元MIDIを除いた新しい留保群などを別に確保してください。自然な実録音と分離後の音についても別評価が必要です。
