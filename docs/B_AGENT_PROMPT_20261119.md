# 担当Bのエージェントへ、そのまま渡すプロンプト

あなたはBand2Tabの担当Bです。担当Aは認識・学習・評価、BはMac画面・再生同期・編集・譜面表示を担当します。最終的に1台のMacで動かします。まず、Aが作成した小さな受け渡しセットで結合確認を完了してください。新しい学習やモデル一式の移送より優先します。

## 受け取るもの

- リポジトリ： https://github.com/Aoi00000/music_ai_exp
- Aの作業ブランチ：`codex/a-training-20261117`
- 受け渡しZIP：`band2tab_AB_integration_20261119.zip`（3,380,045 bytes、約3.38 MB）。音源を含むためGitには置いていません。ユーザーから別途受け取ってください。
- ZIPのSHA256：`ba6ebcd6a1c6f4c1f3e1f8484ef5c9c55e30a8ff3894c42f1171644a687b71ba`
- Git上の記録：`docs/measurements/B_HANDOFF_20261119.json`
- Aの実行手順：`docs/MAC_BAND_HANDOFF.md`

ZIPには同じ12秒区間の`original.wav`、`stems/guitar.wav`、`stems/bass.wav`、`baseline/notes.json`、`review/notes.json`、`review/suggested_notes.json`、`chords.json`、`timing.json`、`model_manifest.json`、`checksums.json`などがあります。基準JSONは途中省略していない完全な結果です。モデル重み・認証は含みません。

## Aで確認済みのことと、未確認のこと

- BabySlakh/Slakhの合成バンド12秒を、HTDemucs 6s → MuScriptor **medium**、CPU float32で新しく解析しました。G/B以外の音符は表示対象から除いています。
- ギター90音、ベース134音を保存。これは検出件数で、正しく当たった件数ではありません。既に使った訓練区間による**結合確認用**で、未知バンドの性能評価ではありません。
- 原音・両ステム・両音符JSON・コードJSONは、入力先頭を同じ0秒として12秒です。canonical mixが原音からの変換と一致すること、補正前音符が基準と一致することを確認済みです。分離の音響的な誤差やモデル時刻誤差がゼロという意味ではありません。
- 今回、補完器は66候補を調べましたが、追加0・削除0です。**補正案は基準と同一**でした。架空の改善や変更を作らず、そのまま示してください。
- `timing.json`のBPM・拍子・最初の小節頭はすべて**未確認（null）**です。コード解析の推定BPMは参考値です。MIDIの120 BPMは仮値で、曲のテンポとして採用しないでください。
- Aの単発CPU測定：分離＋Mu約31.7秒、別AI候補＋補正案約15.1秒。あなたの16 GiB Macやsmallの速度・メモリ・精度を表す値ではありません。
- Bの画面への読込・編集・再保存・原音との再生同期・MusicXML出力、および画面からAの分離＋採譜を一括実行する受入確認は、**これから**です。Aで完了したと扱わないでください。

## 実施順序

1. 現在の作業・未コミット変更・既存テストを確認し、Bの変更を保護してください。統合用の別ブランチを作り、A/B双方が触っている`app.py`は差分を確認して統合します。A版で丸ごと置き換えないでください。
2. ZIPのSHA256を上記と照合して展開し、`checksums.json`の全ファイルを照合します。Aのブランチにある`python3 scripts/a_verify_b_handoff.py '/絶対パス/band2tab_AB_integration_20261119.zip'`でも検証できます。実行場所は取得した`music_ai_exp`のルートです。
3. **再推論せず**、原音と`baseline/notes.json`を画面へ読み込みます。`parts.guitar` / `parts.bass`の音高はMIDI番号、`onset` / `offset`は秒です。全224音を保持してください。データセット原曲の切り出し開始時刻を再加算しません。活動判定は`onset <= t < offset`です。
4. 基準と補正案を別の状態で保持してください。`review/notes.json`では`parts`と`raw_parts`は基準、`suggested_parts`が補正案です。`parts`だけ読む処理には`review/suggested_notes.json`を明示選択で使えます。今回の同一結果を「改善した」と説明しないでください。
5. 原音・必要なら両ステムを聴いて、実際に確認できた誤りを**1か所だけ**修正してください。`reference/notes.json`は既存データの参照ラベルとして補助に使えますが、音を聴いた確認の代わりや全自動の置換には使わないでください。基準・補正案・人の修正版を別に保存します。未編集の音、ベース／他パート、元結果、拍設定が変わらないことを比較し、再読込で確かめてください。
6. 再生位置とギター／ベースの音一覧・TABを同じ時刻で連動させます。`chords.json`の区間に従ってコード予測を併記し、コード外の実音も残してください。まず秒表示とし、拍情報を推測で埋めないでください。BPM・拍子・小節頭を利用者が確認できてから量子化・MusicXML保存まで確認します。
7. 小セットの確認後、画面からAの`scripts/a_band_pipeline.py`を呼ぶ経路を追加します。既存の直接ミックス認識を基準として残し、分離＋Muと比較できるようにしてください。`scripts/a_addition_apply.py`による補正は別環境で任意に実行し、自動上書きしません。最初は10〜12秒で、モデルサイズ・計算場所・所要時間・最大メモリ・空き容量を記録します。必要な重みだけを導入し、Aの仮想環境をそのままコピーしないでください。
8. ファイル選択→解析→比較→編集→MusicXML保存の一連の操作を確認し、成功例・失敗例・保存済み結果での代替デモを固定します。未完了なら具体的な障害と再現手順を報告してください。

## 認識コマンドの契約

以下は**BのMac上のリポジトリルート**で実行します。環境と重みを用意した後に実行し、`/絶対パス/...`は実ファイルへ置き換えてください。毎回新しい出力フォルダを指定します。

```bash
PYTHONPATH="$PWD" .venv-mu/bin/python -m scripts.a_band_pipeline \
  '/絶対パス/入力音源.mp4' --out results/b_integration_baseline --seconds 12
```

出力：`native.wav`、`stems/guitar.wav`、`stems/bass.wav`、`raw_guitar.mid`、`raw_bass.mid`、`notes.json`。音符JSONに`bpm`がなくてもエラーにせず、拍未確認の状態を扱ってください。AのコマンドにBPMだけ渡して生成される`score_input.json`も、小節頭や拍子まで確認済みの保証にはなりません。

コード経路は別コマンドです。同じ入力・時刻原点で実行します。

```bash
OMP_NUM_THREADS=2 PYTHONPATH="$PWD" .venv-yourmt3/bin/python \
  -m chordchart.export '/絶対パス/入力音源.mp4' --out results/b_integration_chords
```

補足：JSON内の`source_analysis`等のA側絶対パスは来歴です。B側でその場所を開こうとせず、ZIP内の上記ファイルを使ってください。Aの音符JSONは生の認識結果であり、Bの譜面JSONの`issues`・運指・拍設定が初めから入った形式ではありません。生結果を保管したままBの読込処理で変換し、未知の拍を既定値で確認済みにしないでください。
